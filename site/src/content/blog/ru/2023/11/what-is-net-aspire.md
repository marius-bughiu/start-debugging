API и фронтенд могут успешно запуститься, но фронтенд всё равно обратится не к тому порту. В Aspire службы и зависимости между ними описываются в **AppHost**. При локальном запуске Aspire запускает ресурсы и передаёт сведения о подключении службам, которые на них ссылаются.

## Как фронтенд находит API

Пусть AppHost на C# ссылается на два проекта с именами `Api` и `Web`. Пример регистрирует оба проекта как ресурсы и указывает, что веб-службе нужен API:

```cs
var builder = DistributedApplication.CreateBuilder(args);
var api = builder.AddProject<Projects.Api>("api");
builder.AddProject<Projects.Web>("web").WithReference(api);
builder.Build().Run();
```

`WithReference(api)` передаёт веб-проекту сведения о конечной точке ресурса `api`. Клиент с настроенным обнаружением служб может использовать это логическое имя. HTTP-запрос по-прежнему отправляет фронтенд, а обрабатывает его API. Если ресурсом служит база данных, тот же механизм может передать строку подключения.

## За что отвечают остальные части

Проект **ServiceDefaults** в стартовом шаблоне содержит общие настройки обнаружения служб, проверок работоспособности и телеметрии. Каждый участвующий сервис вызывает соответствующие методы расширения. **Панель мониторинга** показывает состояния и адреса ресурсов. По журналам и распределённым трассировкам, которые отправляют службы, можно увидеть, где задержалась загрузка страницы: во фронтенде или в ожидании ответа API.
